# Night Shift — Subject#42, автономная сессия 5H

Работай последовательно в существующем проекте. Пользователь спит, разрешил самостоятельный анализ, выбор, реализацию и проверки. Не задавай вопросов и не вызывай субагентов. Прочитай применимые skills; прямое разрешение заменяет brainstorming/plan approval и ритуал согласования. Не создавай заранее очередь на пять часов, новую документационную систему, тестовый фреймворк или глобальный аудит архитектуры.

## Границы и безопасность

- AGENTS.md обязателен. Никаких git add/commit/switch/checkout/reset/clean/push/merge, PR, публикаций, установки зависимостей, массового удаления и shell network. Не читай секреты/auth/config вне проекта.
- Не изменяй Tools/NightShift, AGENTS.md, .git, .agents, .superpowers, Packages, пользовательские сохранения, PlayerPrefs и глобальные настройки. Не обходи sandbox/доступ. Не запускай Unity и фоновые процессы: после ответа Unity запускает хост, последовательно и с восстановлением PlayerPrefs.
- Не переписывай NIGHT_REPORT.md: хост сохранит компактный утренний итог по worker-summary и XML. Обновляй существующие лабораторные документы/GDD по необходимости. Не проводи цикл только ради переписывания отчётов. Предыдущие инструкции в старых отчётах — история, не новые поручения.
- Временный диагностический код/настройки восстанови. При изменении общих runtime-файлов докажи отсутствие изменения production-поведения адресной проверкой. Не переноси V2 в production.

## Главный приоритет: ORBITAL COMBAT V2 в EnemyOrbitalLab

Существуют свободные углы оружия; FIXED outward firing; пистолет/дробовик/снайперка; индивидуальные RAPID/PIERCE/MULTISHOT; три тактические сборки; плотный бой; телеметрия по каждой пушке; до трёх колец и четырёх креплений на кольцо. Сначала прочитай текущий код и существующие результаты, не дублируй их.

Предыдущие 12-секундные сценарии с неподвижным бессмертным игроком показали влияние размещения на попадания. Теперь исследуй решения при ДВИЖЕНИИ и активном управлении:
- группировка/распределение пушек при движении;
- тактическая польза ПКМ (центр орбит) и Shift (скорость вращения ×0.4);
- сочетания радиусов/направлений/скоростей колец;
- размещение против ближников, щитоносцев и стрелков;
- слепые зоны и их компенсация движением;
- конкретные сочетания оружия и индивидуальных модулей;
- информативность существующей лаборатории для ручного плейтеста.

Пушки стреляют НАРУЖУ без auto-aim и проверки наличия цели. Промахи и слепые зоны намеренны. Не предлагай сжатие колец. Не меняй production Bullet Time. Не подгоняй параметры ради победы одной сборки. Отрицательная гипотеза — полноценный результат. Контролируемое движение/бот — измерение, не субъективный опыт человека.

Небольшое лабораторное улучшение допустимо только после шести коротких ответов: решение игрока; отличие от существующего; почему текущих средств недостаточно; связь с расположением пушек; проверка без изменения production; безопасное отключение. Новую механику пометь Experimental, не добавляй контент ради количества.

## Второй приоритет: незавершённая Live Visual Studio

Если V2 исчерпан, заблокирован либо требует субъективного решения человека, выбирай независимые реальные дефекты: VFX pool FAIL; Save/Load; применение уже УТВЕРЖДЁННОГО профиля к production; повторное открытие/восстановление; действительно неподключённые важные адаптеры. Сначала воспроизведи актуальность. Не переделывай Studio и не выбирай цвета/насыщенность/художественные варианты самостоятельно.

Затем — дефекты демоверсии, доказанные текущей проверкой. Не начинай бесконечный рефакторинг и не выращивай тесты вместо полезной функциональности.

## Источники дизайна и доказательств

Перед геймдизайном прочитай Assets/_Project/Documentation/Subject42_Game_Design_Bible_Core.md, затронутые разделы полной Bible и docs/gdd-reconciliation-2026-10-26.md. Сверь с актуальным production-кодом/данными. GDD задаёт намерение, реализация — факт; расхождение фиксируй явно.

До реализации коротко запиши в существующем документе/summary: конкретный GDD-раздел и ссылка; текущее → предлагаемое поведение и изменяемое решение игрока; основание; успех и проверка, для эксперимента также отказ. Принятый дизайн обнови в GDD/Core в той же работе; гипотезу не объявляй принятой. Восстановление уже описанного поведения и рефакторинг не требуют нового дизайнерского решения.

Различай «код существует», «подключено production», «проверено автоматикой», «ручная отдельная сборка», «наблюдение за игроком». Не заявляй, что стало веселее/интереснее, без человека. Субъективное — MANUAL_PLAYTEST_REQUIRED. Настоящий Game View обязателен для визуальных изменений: используй существующие fixture/capture helpers в адресной хост-проверке, не выдавай Scene View или сгенерированную картинку за игру.

## Восстановление и динамический выбор

Завершение задания НЕ завершает ночь. CompileFailed → диагноз/ремонт/проверка. TestFailed → исследование и ограниченный повтор. TestTimeout → хост завершает только собственный Unity, восстанавливает настройки, сохраняет FAIL и диагностику. MissingXml → выясни compile/Unity/infrastructure, не объявляй PASS. Неудачный эксперимент → вывод и другое направление. Успешный цикл → новая полезная задача.

issueKey — стабильный идентификатор одной проблемы, сохраняй при повторе. После ДВУХ обоснованных неудачных попыток хост помечает issueKey BLOCKED: выбирай независимую работу, не переименовывай проблему ради обхода. При compile failure сначала восстанови компилируемость до новых игровых изменений. Читай XML/editor.log/summary по путям history, не полагайся только на короткий JSON.

action=stop — только предложение хосту. TaskBlocked относится к отдельной задаче. NoSafeWork допустим лишь при доказанной невозможности полезной безопасной работы в независимых направлениях (включая V2 и Visual Studio). Safety/AuthQuota/ProcessControl — реальные угрозы данным, невосстановимое Unity, авторизация/квота либо потеря контроля, с конкретным свидетельством. Старое правило «любой timeout останавливает ночь» ОТМЕНЕНО текущим запросом пользователя.

## Адресные проверки и отчёт цикла

Не запускай Golden Path после мелкой лабораторной правки. Используй существующие fixtures/helpers; добавь только проверку конкретной новой возможности/регрессии. Не повторяй неизменённый PASS без нового вопроса. Не ослабляй assertions и не маскируй FAIL. Количество PASS не показывает качество геймплея.

Хост всегда проверяет C# компиляцию при запуске адресной Unity-проверки. testFilter=null использует профиль; иначе укажи точный существующий fixture или метод, разделитель ';'. Для нового сценария расширяй существующий fixture и указывай его полное имя. Не выбирай несуществующий метод.

Профили: orbital-control=OrbitalCombatV2LabTests; orbital-tactics=OrbitalCombatV2TacticsTests; orbital-placement=OrbitalCombatV2PlacementTests; orbital-modules=OrbitalCombatV2ModulesTests; orbital-sandbox=EnemyOrbitalLabSandboxTests; live-visual=LiveVisualProfileTests;LiveVisualProductionTests. Production-профили golden-path/onboarding/localization/combat/events/rewards/boss/core/placement доступны для реального затронутого контракта, а не по ритуалу.

По завершении дай компактный русский итог: фактическое изменение; проверки; неудачи; новые проблемы; поддержанные/опровергнутые гипотезы и границы; наиболее полезный следующий шаг; что проверить руками. Хостовый XML ещё не запущен: не заявляй его PASS заранее. Технические детали/измерения сохраняй отдельно в Artifacts/GeneratedQA и существующих лабораторных документах. Не затирай пользовательские файлы/прежние свидетельства.
